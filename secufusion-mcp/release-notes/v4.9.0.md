## Summary
`/sfn-review` now runs three extra lanes in every review (merge regressions, silent behavior changes, PR scope drift), keeps to a strict role boundary (detect, explain, report; never maintain the code), and searches the story's recorded sources before it may call a behavior change's intent unconfirmed.

## Added
- `check_merge_regressions`: finds functionality accidentally lost while a merge was resolved. It compares the merge commit with both parents and the merge base and reports, as POSSIBLE MERGE REGRESSION with evidence, methods, controller endpoints, repository methods and query predicates, security and authorization checks, tests, configuration keys, translation keys, OpenAPI/Swagger annotations, documentation headings and unexpected signature changes. Severity HIGH (security, authorization, endpoint, repository query), MEDIUM (methods, tests, config, signatures), LOW (translations, OpenAPI, docs). It uses git's three-way logic, so a deletion one parent made deliberately and the merge honoured, and a method that moved to another file, are not reported. It also scans a merge in progress. It is read-only.
- `check_behavior_changes`: surfaces behavior that changed while the code compiles and tests pass: authorization checks, validation, query predicates, filtering, default values, feature flags, conditionals and time calculations, with signals for how each changed (operator flipped, value changed, predicate dropped, negation added, line removed). The reviewer writes a BEHAVIOR CHANGE block per change: old and new behavior, affected users, acceptance-criteria impact, risk, intent explicitly confirmed.
- Intent evidence search: with `work_item_id`, `check_behavior_changes` searches the acceptance criteria, story text (requirement, plan, specification), ADRs and recorded product decisions for possible support under each change, and says plainly when the search was not run. The reviewer must search all five sources (including the user's instructions) and state what it searched before writing "intent not confirmed".
- `check_scope_drift`: classifies changed files as core story files, indirectly related files or unrelated files from the story's plan and acceptance criteria, and reports each unrelated file as SCOPE DRIFT with the recommendation to move it to a separate story or explain why it is included.
- Reviewer role boundary: the reviewer detects, explains and reports. It never deletes or restores code, removes methods, chooses develop (or any branch) automatically, or rewrites files without a request. When unsure it reports DEVELOPER DECISION REQUIRED with decision, evidence and rationale, in its own report section.
- Story scope classes: every finding is Class A (in scope), B (adjacent) or C (future); only Class A decides the verdict. Report order: story scope assessment, in-scope findings, out-of-scope observations, future considerations, verdict.

## Changed
- Files outside the plan are reported as scope drift and never fail a review. `out_of_scope_changes` in `verify_against_spec` is reserved for work the specification explicitly excludes or a recorded user decision forbids. The review text, the server rubric and the tool guidance agree.
- An unconfirmed behavior change with HIGH risk is an in-scope BLOCKER and with MEDIUM risk an in-scope WARNING; confirmed or LOW-risk changes are informational.
- Merge-regression findings never change approval status unless one directly impacts an acceptance criterion.
- The report gains sections for merge regression findings, behavior changes, scope drift and developer decisions required, and the findings summary lists each lane.
- The tool count is now 77.

## Fixed
- A file that merely sat outside the plan could block approval through `out_of_scope_changes`, although it said nothing about whether the change was right.
- A pre-existing problem in code the change did not touch, or a long-term suggestion, could be raised as something this story must fix.
- A behavior that moved silently (a flipped comparison, a changed default, a dropped predicate) had no place in the review and could pass because the build and tests stayed green.
- Functionality lost in a merge resolution could be mistaken for dead code.

## Breaking changes
None for commands, existing tools or their parameters. Behavior to know about: a review that listed out-of-plan files as `out_of_scope_changes` will now report them as scope drift instead, and a new ADR or review that relied on the old blocking behavior will no longer be blocked by it.

## New tools
`check_merge_regressions`, `check_behavior_changes`, `check_scope_drift`.
